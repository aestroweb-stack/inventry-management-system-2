# R20 Visual Search — phase 1

Apply over R19. Back up seller workspaces before updating. The existing isolated seller SQLite databases remain authoritative. The new `local_visual_vectors_v1` table is created by the existing SQLAlchemy `create_all` on startup / seller workspace initialization; no existing inventory table is replaced. NumPy is declared as a dependency. Existing photos are embedded lazily on their first search, and future photo uploads index in existing background tasks. Failed index writes are retried during a future search. Cold searches may take a long time if many photos require embedding, especially with remote SigLIP.

- No fixed catalog-size or total gallery-count cap in the changed visual search and gallery code. Add Product uploads sequential groups of up to eight; Edit saves up to eight NEW photos at once while preserving any number of saved photos. Each photo remains limited to 10 MB and validated. Result shortlist and per-seller search rate limits remain intentional.
- SQLite search uses keyset batches of 256 reference rows, float32 vectorized exact cosine scoring, one best image per design, and a bounded Top-K heap. Complexity is still linear in the number of reference vectors, O(N*d + P log k), not a distributed ANN system. Derived vectors are scoped to the seller database; they are not authoritative stock data. A replaced image invalidates cached features by path/file metadata/model. Removed catalog rows cannot match; stale derived rows can remain on disk.
- Test results: synthetic cached vectors over 3,101 designs; separate databases with overlapping product/image IDs; lazy cache, replacement, deduplication across batches; 11-photo editor save; R13/R16 regression tests. Barcode library was unavailable in the test environment; a temporary import stub that fails if barcode generation is invoked was used for editor regression tests. No live Clerk, Railway, actual SigLIP, concurrent production workload, or billion-scale benchmark was run.
- Existing recovery service has a safety cap of 5,000 media files per recovery point. Deletion and editor-save may be blocked above that threshold until scalable backup storage is implemented. Do not bypass this guard. The derived vector table also adds size to local recovery snapshots. Existing local galleries and inventory API responses are not paginated at image level. Large catalog production rollout requires migration and capacity tests.

## Phase 2 (design only, not included)
Use a separate private distributed Qdrant deployment with tenant-scoped HNSW indexes, per-tenant shard routing, durable indexing queue, object storage for images, backups and reconciliation for deletion/replacement. Separate an opt-in licensed shared reference catalog from private seller inventory. Search global references only if authorized; never infer seller stock from a public reference. Evaluate quantization, recall@k, p95 latency and concurrent load with real garments. One billion 768-dimensional float32 vectors alone occupy about 3.072 TB before indexes, replica copies, metadata or photographs. No latency SLA is implied by this patch. Missing images cannot be matched to a real SKU without reference data; retain manual SKU, QR or catalog import.
